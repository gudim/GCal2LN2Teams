# Эталонные планы движка синхронизации

Приёмочная спецификация движка синхронизации (`mobile/shared/.../sync/`). Каждый файл
`golden/<сценарий>.json` — это состояние календарей и связей перед запуском и всё, что движок
должен из него получить. Изначально эталоны сгенерировала Python-версия при переносе движка на
Kotlin (`docs/adr/0002-mobile-kmp-on-device.md`); Python-версия удалена, эталон теперь —
Kotlin-движок (ADR 0005).

- Проверка: `GoldenPlansTest` (`./gradlew :shared:jvmTest` из `mobile/`) прогоняет
  `runGolden` на каждом файле и сравнивает с `expected`.
- Новый сценарий или изменение поведения: впишите `input`, получите вывод `runGolden` для этого
  файла, проверьте его глазами и запишите в `expected`. Изменение эталона — это изменение
  поведения: смотрите diff.
- `fixtures/` — ответы API Google, Domino и MS Graph для тестов адаптеров (см. `fixtures/README.md`).

## Общие соглашения

**Системы** — строки `"google"`, `"domino"`, `"teams"`. Канонический порядок систем —
**google, domino, teams** (`ORDER` в движке). Он влияет на результат: в каком порядке
обходятся календари, какая система пары считается первой при поиске двойников, кто корень
группы связанных событий. Везде, где в файле перечислены системы (пары, маршруты), они
записаны в этом порядке.

**Время.**
- Время события — момент в UTC: `"2026-11-13T10:00:00Z"`.
- Дата (событие на весь день) — `"2026-11-13"`. Отличить можно по длине строки: 10 символов —
  дата. У события `start` и `end` либо обе даты, либо оба момента.
- `end` у событий на весь день **исключён**: однодневное событие 13 ноября — это
  `"start": "2026-11-13", "end": "2026-11-14"`.
- Снимки полей (`source_fields`/`target_fields`) и ключи действий содержат время в другом
  виде — так, как его пишет `CalendarEvent.fields()`: `"2026-11-13T10:00:00+00:00"`. Эти
  строки хранятся в связях и сравниваются как строки, поэтому Kotlin обязан выдавать ровно
  такой текст (см. «Снимок полей»).

**JSON.** Файлы записаны с `sort_keys`, отступом 2 и UTF-8 без экранирования. Порядок ключей
в объектах значения не имеет; сравнивайте разобранный JSON, а не текст. `null` — отсутствие
значения. Python-представлений (`None`, `True`, `datetime(...)`) в файлах нет.

**Порядок списков.**
- Во входе списки отсортированы: события календаря — по `id`, связи — по `key`. Движок
  получает их **именно в этом порядке**, и от него зависит порядок действий.
- `expected.plan.actions` — в порядке, который выдаёт движок. Порядок значим: `apply`
  выполняет действия по очереди, а `depends_on` ссылается на уже выполненные. Kotlin должен
  выдать тот же порядок.
- Остальные списки результата отсортированы (см. описание полей).

## Событие

| Поле | Тип | Смысл |
|---|---|---|
| `id` | строка | id события в его системе |
| `title` | строка | название **без** маркера `[GC]`/`[LN]`/`[MT]`; пробелы схлопнуты |
| `start`, `end` | момент или дата | см. «Время» |
| `location` | строка | место |
| `description` | строка | описание |
| `source` | система или `null` | из какой системы событие скопировано; `null` — оригинал |
| `uid` | строка или `null` | iCalendar UID, общий для одной встречи в разных системах |
| `original_start` | момент/дата или `null` | исходное начало экземпляра серии (RECURRENCE-ID) |
| `organizer_is_me` | bool | `false` — чужая встреча: синхронизатор её не меняет и не удаляет |
| `has_attendees` | bool | правка оригинала разошлёт письма участникам |
| `private` | bool | частное событие (копия тоже частная) |
| `modified` | момент или `null` | время последнего изменения на сервере |
| `ignored` | bool | служебное/отклонённое/отменённое: не копируется, копии удаляются |

Ключи, которые использует движок:
- **ключ копии** (`match_key`): `title` + `start` (точное совпадение);
- **ключ кандидата в двойники** (`twin_key`): `title` без учёта регистра (Python `casefold`) +
  `start`;
- **ключ двойника по UID** (`uid_key`): `uid` + (`original_start`, а если его нет — `start`);
  без `uid` ключа нет;
- **ключ кандидата в двойники по времени** (`time_key`): `start` + `end`; у событий на весь
  день ключа нет.

Окно `[start, end)` пересекается с событием, если `event.start < window.end` и
`event.end > window.start`; для событий на весь день границы окна берутся как даты (UTC).

## Снимок полей

Объект из пяти строк — `CalendarEvent.fields()`, нормализованный вид синхронизируемых полей:

| Поле | Как получается |
|---|---|
| `title` | название (пробелы уже схлопнуты в одиночные, края обрезаны) |
| `start`, `end` | момент: `YYYY-MM-DDTHH:MM:SS+00:00` (если есть микросекунды — `YYYY-MM-DDTHH:MM:SS.ffffff+00:00`); дата: `YYYY-MM-DD` |
| `location` | пробельные символы схлопнуты в один пробел, края обрезаны |
| `description` | края обрезаны, у каждой строки обрезаны пробелы справа, строки соединены `\n` |

Поля сравниваются группами: `title`; `start`+`end` (меняются вместе); `location`;
`description`.

## Связь

| Поле | Тип | Смысл |
|---|---|---|
| `key` | строка | вычисляемый ключ (при чтении не нужен, но Kotlin должен вычислять такой же) |
| `kind` | `"copy"` / `"twin"` / `"distinct"` | оригинал→копия; двойники; «это разные встречи» |
| `source_system`, `source_id` | | для `copy` — оригинал |
| `target_system`, `target_id` | | для `copy` — копия; `target_id` может быть `null` |
| `source_fields`, `target_fields` | снимок или `null` | поля сторон после прошлой синхронизации; `null` у старых связей и у `distinct` |
| `kept` | bool | одна сторона удалена, другую оставили: не спрашивать и не воссоздавать |

**Отказ от копирования** — связь `copy` с `kept: true` и `target_id: null`: пользователь снял
галочку с создания копии при ручном применении (ADR 0003). Ключ у неё тот же, что у будущей
связи копии (`google:g1->domino`), поэтому созданная позже копия заменяет отказ. `collect` её не
проверяет (она `kept`).

Ключ связи:
- `copy`: `<source_system>:<source_id>-><target_system>`, например `google:g1->domino`;
- иначе: `<kind>:<source_system>:<source_id>-><target_system>:<target_id>`, например
  `twin:google:g1->domino:d1`.

## Действие

| Поле | Тип | Смысл |
|---|---|---|
| `key` | строка | стабильный ключ между предпросмотром и запуском (см. ниже) |
| `kind` | строка | `create`, `update`, `delete`, `twin` — видимые; `link`, `unlink` — служебные |
| `origin` | система | откуда изменение (система оригинала / победившей стороны) |
| `target` | система | где выполняется действие |
| `event` | событие или `null` | `create`: будущая копия (`id` и все поля оригинала, `source` = система оригинала); `update`: новое содержимое события с `id` цели; `delete`: удаляемое событие; `twin`: двойник в `target`. У `link`/`unlink` — `null` |
| `selected` | bool | галочка по умолчанию в предпросмотре |
| `silent` | bool | не показывается и выполняется без подтверждения |
| `reason` | строка | текст для пользователя (на русском), может быть пустым |
| `subject` | строка | только у `delete`: `copy`, `extra` (лишняя копия), `original`, `twin`; иначе `""` |
| `changed` | список строк | только у `update`: изменённые поля в порядке `title, start, end, location, description` |
| `depends_on` | список ключей | выполнять, только если эти действия уже выполнены в этом запуске |
| `link` | связь или `null` | `link`: связь, которую сохранить; `unlink`/`delete`: связь, которую убрать; `twin`: связь двойников |
| `fallback` | список действий | что выполнить вместо этого, если ключ не выбран пользователем (только когда ключи переданы). У `create` оригинала с `id` — служебный `link` с отказом от копирования |

Ключ действия:
- `create`: `<origin>:<event.id>><target>`, например `google:g1>domino`; если у события нет
  `id` — `<origin>:<title>@<start как в снимке>><target>`;
- `link`, `unlink`, `twin`: `<kind>:<ключ связи>`, например `twin:twin:google:g1->domino:d1`;
- `update`, `delete`: `<kind>:<target>:<event.id>`, например `delete:google:g1`.

## Файл сценария

```json
{
  "name": "update_original_change",
  "description": "что проверяет сценарий",
  "input": { ... },
  "expected": { ... }
}
```

### input

| Поле | Смысл |
|---|---|
| `window` | окно синхронизации `{"start", "end"}`, моменты в UTC |
| `direction` | направление из UI (`all`, `google-domino`, `google-teams`, `domino-teams`), для справки |
| `pairs` | пары систем, синхронизируемые в обе стороны (раскрытый `direction`); используйте их |
| `calendars` | `{система: [событие, ...]}` — **всё** содержимое календаря, в том числе события вне окна. Есть только системы, календари которых прочитаны |
| `links` | связи из хранилища перед запуском |
| `select.keys` | ключи, отмеченные в предпросмотре; `null` — ключей нет (выбор по умолчанию, как фоновая синхронизация) |
| `select.routes` | маршруты `[[origin, target], ...]`; `null` — все |
| `failures` | `[{system, operation, title}]`: в календаре `system` операция `create`/`update`/`delete` над событием с таким названием падает с ошибкой `"сбой"` |
| `unavailable` | **необязательное**, по умолчанию `[]`: системы, которые в этом запуске не прочитаны из-за сбоя (Domino не ответил или выключен после 401), в каноническом порядке. Их календарей в `calendars` нет. См. «Недоступная система» |

Пара участвует в плане, только если прочитаны календари обеих её систем.

### Как прогонять

1. Создать календари в памяти в порядке google, domino, teams (только те, что есть в
   `calendars`), с событиями в порядке файла. Календарь в памяти:
   - `list(window)` — события, пересекающие окно, в порядке хранения;
   - `get(id)` — событие с этим `id` (в том числе вне окна) или «нет»;
   - `create(event)` — назначает `id` = `<система>-new-<n>`, где n — номер вызова `create` в
     этом календаре с 1; остальные поля события сохраняет как есть; добавляет в конец;
   - `update(id, event)` — заменяет `title`, `start`, `end`, `location`, `description`,
     остальные поля не трогает;
   - `delete(id)` — убирает событие; удалять несуществующее — не ошибка;
   - сбой из `failures`: `create`/`update` сверяют `title` из события действия, `delete` —
     название удаляемого события.
2. `collect`: прочитать `list(window)` каждого календаря; затем для каждой связи, кроме `kept`,
   `distinct` и закончившихся до окна (обе стороны есть в снимке и обе кончились не позже
   начала окна), вызвать `get` для каждой стороны, которой нет в прочитанном и которую ещё
   не запрашивали.
3. `plan(snapshot, pairs, links, found, unavailable)`.
4. `select(actions, routes, keys, refused)`, где `refused` — `plan.refused`: если ключи переданы,
   после остальных действий добавляются отказы, чьи ключи есть в `keys` (в пределах маршрутов).
5. `apply(выбранные, календари, хранилище связей)`. Хранилище — упорядоченная карта по ключу
   связи: `save` заменяет связь с тем же ключом, `drop` удаляет по ключу.
6. Состояние после `apply` — заново как вход (события по `id`, связи по `key`) — прогнать
   ещё раз через шаги 1–3 с тем же `unavailable`: это `replan`.

### expected

| Поле | Смысл |
|---|---|
| `collect.listed` | `{система: [id, ...]}` — что вернул `list(window)`, в порядке календаря |
| `collect.fetched` | `[{system, id, event}]` — что запросили через `get`; `event: null` — события нет. Отсортировано по `system`, затем `id` |
| `plan.actions` | действия плана в порядке движка |
| `plan.warnings` | предупреждения (тексты на русском) |
| `plan.refused` | отказы в окне: действия `create`, которые план предложил бы без отказа, в порядке движка; `link` — связь-отказ, `fallback` пуст. В `actions` их нет |
| `select` | ключи действий, которые вернул `select`, в его порядке (сюда попадают и действия из `fallback`) |
| `apply.report` | счётчики `apply` по маршрутам: `{origin, target, created, updated, deleted, linked, errors}`; только маршруты с ненулевым счётчиком или ошибкой; отсортировано по `origin`, затем `target`. `linked` считает только `twin`; ошибка — `"<название из события действия>: сбой"`. Действие, пропущенное из-за `depends_on`, не считается |
| `apply.calendars` | содержимое календарей после `apply`, события по `id` |
| `apply.links` | связи после `apply`, по `key` |
| `replan` | план (`actions`, `warnings`, `refused`) повторного запуска на результате. Пустой — значит, нет эха; непустой — вопрос остался открытым или действие не выполнилось |

## Сценарии

| Сценарий | Что проверяет |
|---|---|
| `create_all_directions` | Оригинал в каждой системе копируется в две другие: шесть маршрутов. Частное событие копируется со всеми полями. |
| `direction_limits_pairs` | Направление google-teams: Domino не участвует, хотя его календарь прочитан. Все три события в одно время: у Google и Teams вопрос по времени без галочки (без ключей ничего не копируется), у Domino — нет. |
| `copies_are_not_copied_further` | Копия ([GC] в Lotus) не копируется дальше в Teams. |
| `already_linked` | Связь со снимком, обе стороны не менялись: ничего не делать. |
| `old_link_without_snapshot` | Старая связь без снимка: копия не создаётся заново и не обновляется, связь получает снимок текущих полей (служебное действие link). |
| `legacy_match_by_marker` | Копии без связи (сделаны до появления связей) узнаются по source + название + начало (в UTC, 01:00 МСК = 22:00 UTC). Ни копий, ни связей не создаётся. |
| `legacy_match_needs_same_start` | Копия без связи с другим началом не считается копией: оригинал копируется. |
| `update_original_change` | Изменили название оригинала: обновляется копия, затем снимок связи. |
| `update_copy_change_to_original` | Изменили место в копии: правка уходит в оригинал без участников. |
| `update_merge_different_fields` | Разные поля изменены с двух сторон: оба изменения сливаются в обе стороны. |
| `conflict_later_modified_wins` | Одно поле изменено с двух сторон: побеждает более позднее modified. |
| `conflict_tie_goes_to_original` | Одно поле изменено с двух сторон, у одной стороны нет modified: побеждает оригинал. |
| `update_original_with_attendees` | Правка копии должна уйти в оригинал с участниками: вопрос без галочки «участники получат письмо». Без ключей не выполняется и задаётся снова. |
| `update_original_with_attendees_confirmed` | То же, но пользователь отметил обновление в предпросмотре. |
| `foreign_meeting_copy_change_ignored` | Чужая встреча не меняется: правка копии только попадает в снимок связи. |
| `foreign_meeting_change_wins` | Чужая встреча и копия изменены: изменения берутся только из чужой встречи, даже если копия изменена позже. |
| `copy_change_propagates_to_other_copies` | Копию в Lotus перенесли: обновляется оригинал, а после него — копия в Teams. |
| `event_moved_out_of_window` | Оригинал перенесли за окно: get() его находит, копия обновляется, а не удаляется. |
| `twins_sync_fields` | Двойники синхронизируют поля так же, как оригинал и копия. |
| `apply_failure_skips_dependent` | Обновление копии упало: снимок связи не обновляется (depends_on), в следующий раз обновление планируется снова. |
| `delete_copy_when_original_gone` | Оригинал удалён: копия удаляется без вопроса (silent), связь убирается. |
| `delete_copy_of_ignored_original` | Оригинал стал служебным/отклонённым (ignored): копия удаляется; ignored-событие без копии не копируется. |
| `copy_gone_asks_to_delete_original` | Копию удалили: вопрос «удалить оригинал?» без галочки. Без ключей ничего не делается, вопрос задаётся снова. |
| `copy_gone_original_delete_confirmed` | Копию удалили, пользователь отметил удаление оригинала. |
| `copy_gone_declined_is_kept` | Копию удалили, пользователь не отметил удаление: связь запоминается как kept. |
| `kept_link_not_recreated` | Связь kept: копия не воссоздаётся и вопрос не задаётся. |
| `copy_of_foreign_original_gone_kept_silently` | Удалили копию чужой встречи: оригинал не трогаем, связь молча становится kept. |
| `twin_gone_asks_and_foreign_twin_never` | Двойники удалены в Lotus: вопрос об удалении своего двойника в Google, чужой не трогаем. Пользователь отказался: обе связи kept. |
| `mass_delete_by_count` | Исчезло больше 5 оригиналов: все удаления без галочек и видимы, предупреждение. |
| `mass_delete_by_share` | Исчезло 4 оригинала из 10 связей (40% > 30%): защита срабатывает. |
| `mass_delete_below_threshold` | Исчезло ровно 30% (3 из 10): защита не срабатывает, копии удаляются молча. |
| `mass_delete_few_links` | Исчезли все 5 оригиналов, но связей меньше 10 и оригиналов не больше 5: защита не срабатывает. |
| `twins_by_uid` | Один UID в двух системах: двойники связываются сразу, копии не создаются. |

## Двойники по времени и отказы (ADR 0003)

**Вопрос по времени.** Два оригинала в разных системах активной пары с одинаковыми `start` и
`end`, но разными названиями (`twin_key` отличается) — вопрос `twin` «одинаковые начало и
конец, разные названия: это одна встреча?» с `selected: false`. Ключ и связь — как у вопроса по
названию (`twin:twin:<s1>:<id1>-><s2>:<id2>`, s1 — первая система пары в каноническом порядке).
Поиск идёт в каждой паре после UID и названия, с тем же набором `used`: событие, уже ставшее
кандидатом по UID или названию, по времени не рассматривается, и вопрос по названию выигрывает.
Связь `distinct` между ними вопрос отменяет. Решения о шуме:

- **Только оригиналы.** Копии (`source` не `null`) и `ignored` не участвуют, как и везде.
- **Без событий на весь день.** Праздники, отпуска и дни рождения в разных календарях часто
  совпадают датами, а разными встречами быть не перестают: ключа у них нет.
- **Чужая против чужой — спрашиваем.** Типичный дубль — организатор сам продублировал встречу во
  вторую систему с другим названием («дублирую в тимсе»): для владельца календаря обе встречи
  чужие. Шум ограничен: галочка снята, и после первого ручного применения запоминается `distinct`.
- **Несколько кандидатов** — первый с первым по порядку календарей, как у вопроса по названию;
  остальные копируются как обычно. Если пользователь ответит «нет», в следующий раз может
  появиться вопрос для следующей пары.
- **Копии между кандидатами — ответ «нет».** Как у вопроса по названию, они лежат в `fallback`
  вопроса. Поэтому, пока вопрос открыт, фоновый запуск (без ключей) не копирует кандидатов друг в
  друга и не удаляет лишние копии (их удаления зависят от вопроса через `depends_on`). При ручном
  применении без галочки выполняется `fallback`: копии и `distinct`.

**Лишние копии в третьей системе.** Если у группы двойников (в том числе кандидатов) нет своего
события в системе S, но в S лежат копии разных членов группы, остаётся одна: копия того члена,
который копирует за группу (первый в каноническом порядке, у кого есть пара с S, — как при
создании), а если её нет — первая по порядку календаря. Остальные удаляются как `extra` с
причиной «лишняя копия: в календаре уже есть копия двойника»; `depends_on` — вопросы группы, если
оставленная и удаляемая копии не связаны подтверждёнными двойниками.

**Отказ от копирования.** У каждого `create` оригинала с `id` есть `fallback`: служебный `link` с
отказом. Значит, снятая галочка при ручном применении (ключи переданы) запоминает отказ, а
фоновый запуск (без ключей) отказов не создаёт. Создания из `fallback` вопроса о двойниках своего
отказа не имеют. Если для (система оригинала, id, цель) есть отказ, а группа ещё не покрыта
подтверждёнными двойниками, создание уходит в `plan.refused` вместо `actions`. Отказ снимается
двумя способами: ключ из `refused` в `keys` (копия создаётся сейчас) или `undo_refusal` (удалить
связь; копия будет предложена в следующем плане). Старые связи `kept` с `target_id` и `distinct`
работают как раньше.

Пороги защиты от массового удаления: больше 5 исчезнувших оригиналов за запуск, или у
какой-то системы не меньше 10 связей и исчезло больше 30% из них (строго больше: 3 из 10 —
ещё нет). Исчезнувший оригинал — оригинал связи `copy` или сторона связи `twin`.

## Недоступная система

`unavailable` — системы, которые не прочитаны из-за сбоя в этом запуске. Это не то же самое, что
система, выключенная направлением или маршрутами: та просто не участвует в парах, а связанные с
ней события синхронизируются как раньше (`direction_excluding_lotus_is_not_outage`).

**Заморозка.** События соединяются связями `copy` (в любую сторону) и `twin`, транзитивно, в
группы. Связи `kept` (вторая сторона уже удалена), `distinct` и отказы (без `target_id`) события
не соединяют. Если в группе есть событие недоступной системы, вся группа заморожена: ни для
одного её члена, в какой бы системе он ни был, план не содержит `create`, `update`, `delete`,
`twin`, служебных `link`/`unlink`, отказов в `refused` и вопросов. Конкретно:

1. Связь, концы которой заморожены, при разборе существующих связей пропускается целиком: она
   не попадает в живые связи (обновления), не порождает удалений и вопросов и **не считается** в
   защите от массового удаления (ни в число связей системы, ни в исчезнувшие оригиналы).
   В «уже скопировано» (`copied`) и `twinned` она по-прежнему попадает.
2. Поиск новых двойников видит замороженные оригиналы как обычно (они занимают место в `used`),
   но если в найденной паре (по UID, названию или времени) есть замороженный, ни связь, ни
   вопрос не создаются, а **второй тоже замораживается** до конца плана: кандидат ждёт вместе с
   группой, а не копируется (`unavailable_candidate_twin_waits`).
3. Лишние копии: замороженная копия, а также копия, чей оригинал (по связи или маркеру)
   заморожен, не удаляется.
4. Новые копии: замороженный оригинал не копируется.

Группы без связи с недоступной системой планируются как обычно. При пустом `unavailable` план
тот же, что и без поля.
